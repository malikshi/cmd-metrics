cmd-metrics — what each number actually measures

One model request has two phases. Every metric in the mod is a ratio of those phases.

1 · Anatomy of one model request

request
start → end
prefill + thinking · TTFT 1.6s
132 tok
duration
prefill — nothing to show yet generation — tokens streaming first token (TTFT ends here)
TTFT = first token time − request start  =  1.6s
duration = request end − request start  =  2.1s
TPS = outputTokens ÷ (duration − TTFT) = 132 ÷ (2.1 − 1.6) = 132 ÷ 0.5s = 264 t/s

Why subtract TTFT? Prefill is not generation. Dividing 132 ÷ 2.1s would report 63 t/s and blame the model for a slow prompt read. The mod never does that.

If a route delivers the whole answer in one flush, there is no generation timeline to measure: the rate falls back to wall clock and the row prefixes it with ~.

2 · cache % — how much of the prompt was reused

request #1 prompt · 27,947 input tokens
14,336 cache read · 51%
13,611 fresh
cache % = cacheReadTokens ÷ inputTokens = 14,336 ÷ 27,947 = 51%

inputTokens already counts cached tokens — Command Code subtracts cache reads back out before pricing fresh input. So the divisor is the whole prompt, never the fresh slice.

3 · A 3-request session, and where the averages come from

#TTFTdurationout tokTPScacheinput
#11.6s2.1s132264 t/s51%27,947
#21.7s1.8s14140 t/s99%15,000
#32.0s4.0s200100 t/s40%30,000
session1.8s2.6s·168 t/s56%72,947
avg TTFT = (1.6 + 1.7 + 2.0) ÷ 3 = 5.3 ÷ 3 = 1.77s → 1.8s
avg TPS = (264 + 140 + 100) ÷ 3 = 504 ÷ 3 = 168 t/s — one request, one vote
avg duration = (2.1 + 1.8 + 4.0) ÷ 3 = 7.9 ÷ 3 = 2.63s → 2.6s
cache = ΣcacheRead ÷ Σinput = 41,186 ÷ 72,947 = 56% — token-weighted, NOT the average of 51/99/40 (= 63%)
⚠
Token-weighted is the honest one. Averaging percentages lets one tiny cold request cancel out one huge warm prompt. 51 / 99 / 40 averages to 63%, but the real number of cached tokens is 41,186 of 72,947 — 56%. The mod reports 56%.

4 · total tokens — two lines, two totals

session 73,293
⑂ 20,370
input + output, every parent requestsub-agent usage totals
session tok = Σ(parent input + output) = 73,293 → 73k tok
⑂ tok = Σ sub-agent tokens = 20,370 → 20k tok
whole session = 73,293 + 20,370 = 93,663 → 94k tok — the reader adds the two

Each sub-agent is its own inference call billed on its own tokens, so it is reported — on its own line. The session row counts parent requests only, so no parent figure has a child's usage inside it. Both figures are totals, never a mean-per-child: ⑂2 at 6.2M means 6.2M tokens across both children, not 12.4M.

6 · The one approximation, stated plainly

parent request TTFTmeasured
parent TPS · duration · cacheexact
total tokensexact
sub-agent TTFTspawn → first forwarded event
sub-agent TPS · durationexact
child first-token timenot observable
sub-agent cache %no prompt accounting
unobserved first token (cancelled)TTFT — · TPS —
session figures across a reloadrestored by sessionId
older sessionsown key · last 20 kept

Command Code's sub-agent translator consumes a child's own text_delta and never re-emits it, and child runs do not receive user mods — so no mod can see a child's true first token. The earliest observable point is the first forwarded subagent_progress. That is why sub-agent timing never enters the session averages.
